## 1. Threat Model

### 1.1 Assets

| Asset | Sensitivity | Description |
|-------|-------------|-------------|
| User identity & presence | Medium | Name, email, online status |
| Call audio content | High | Real-time voice conversation |
| Call metadata | Medium | Call duration, timestamps, participants |
| Push tokens | Medium | FCM/APNs device tokens |
| Auth credentials | High | JWT secrets, API keys, OAuth tokens |
| TURN credentials | Low | Time-limited credentials for relay |
| Call context from AI | Medium | AI task context passed into calls |

### 1.2 Threat Actors

| Actor | Motivation | Capability |
|-------|------------|------------|
| Unauthorized user | Eavesdrop, disrupt calls | Can attempt API requests |
| Malicious AI agent | Spam calls, extract info | Can invoke MCP tools |
| Network attacker | Intercept media, MITM | On-path between client/server |
| Compromised service | Data exfiltration | Internal access to DB |
| Rogue TURN relay | Record media content | Can relay WebRTC traffic |

### 1.3 Threat Scenarios

| ID | Scenario | Risk |
|----|----------|------|
| T1 | Attacker eavesdrops on WebRTC media without SRTP | Critical |
| T2 | Attacker hijacks a call session via signaling replay | High |
| T3 | Malicious agent spams calls to a user | Medium |
| T4 | Attacker impersonates a user via stolen JWT | Critical |
| T5 | TURN relay operator records audio | High |
| T6 | Push notification spoofing (fake call alerts) | Medium |
| T7 | Call context leak through MCP server output | Medium |

## 2. Authentication & Authorization

### 2.1 User Authentication

**Flows:**
- **OAuth 2.0** with Google/GitHub/Apple as identity providers
- **Device Pairing:** QR-code based flow for headless setup
  - Mobile app scans QR code on web dashboard
  - QR encodes a one-time pairing token (valid 5 min)
  - Server exchanges pairing token for a long-lived refresh token

**Token Strategy:**
- Access Token: JWT, 15-minute expiry, signed with RS256
- Refresh Token: Opaque 128-bit random, stored SHA-256 hashed in DB, 30-day expiry, rotation on use
- JWT Claims: `sub` (user_id), `did` (device_id), `role`, `iat`, `exp`, `jti`

### 2.2 MCP Agent Authentication

**API Key Authentication:**
- Agents authenticate via API keys (prefixed for identification: `icm_xxxx...`)
- Full key stored as SHA-256 hash in `api_keys` table
- Key prefix stored for identification in logs
- Permissions scoped per key (e.g., `["create_call", "query_presence"]`)
- Key rotation supported with overlap period

**Token Exchange:**
- MCP Agent receives a service-to-service JWT after API key validation
- Shorter expiry (5 minutes) for MCP tool invocations
- Scoped to specific call operations

### 2.3 Service-to-Service Authentication

- Internal services communicate via Docker network
- Pre-shared `SERVICE_TOKEN` env variable for HTTP calls
- Redis connections restricted to internal network
- PostgreSQL connections via password auth, restricted by network

## 3. Media Security (WebRTC)

### 3.1 SRTP Encryption

- **Mandatory** SRTP (Secure Real-time Transport Protocol) for all audio
- AES-128 CM encryption with SHA-1 HMAC authentication
- DTLS-SRTP key exchange (DTLS 1.2+)
- Cipher suite: `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256` (preferred)
- Key derivation per RFC 5764

### 3.2 TURN Security

- **TURN credentials are time-limited** (max 1 hour)
- Credentials generated by Auth Service using HMAC-SHA1 with shared coturn secret
- Format: `username=<timestamp>:<user_id>`, `credential=HMAC(secret, username)`
- coturn configured with `use-auth-secret` and `static-auth-secret`
- Protocol: TURN over TLS (port 5349) for control, DTLS for data

### 3.3 ICE and Connectivity

- **ICE restart** on connection loss
- **mDNS candidates** to prevent local IP leakage (Chrome, Safari)
- **IP handling policy:** prefer `srflx` and `relay` candidates; `host` candidates allowed but logged
- STUN binding requests throttled (max 10/s)

## 4. Signaling Security

### 4.1 WebSocket Security

- WSS (WebSocket Secure) only, no unencrypted WS
- JWT authentication on connection (`wss://.../ws?token=<jwt>`)
- Token validated at connection and periodically re-validated (every 5 min)
- One session per `(user_id, device_id)` pair; duplicate connections close old one
- Message rate limiting: 50 messages/second per connection

### 4.2 Anti-spoofing

- Call offer validation: only Call Manager can trigger an `offer` to a client
- Participants must be validated participants of the specific `call_id`
- Signaling server validates all `call_id` references against Redis active calls

## 5. API Security

### 5.1 Rate Limiting

| Endpoint | Window | Limit | Burst |
|----------|--------|-------|-------|
| `POST /api/v1/calls` | 60s | 10 per user | 15 |
| `POST /api/v1/calls/:id/cancel` | 60s | 20 per user | 30 |
| `GET /api/v1/users/:id/presence` | 60s | 60 per user | 100 |
| `POST /api/v1/auth/login` | 60s | 5 per IP | 10 |
| `POST /api/v1/auth/refresh` | 60s | 10 per user | 15 |
| WebSocket signaling | 1s | 50 per connection | 75 |

### 5.2 Input Validation

- All inputs validated with JSON Schema (AJV)
- HTML/script tags rejected (XSS prevention)
- UUIDs validated via regex
- String lengths capped (context: 1000 chars, summary: 500 chars)
- JSONB fields sanitized before storage

### 5.3 CORS & Headers

- Strict CORS policy (whitelist: registered web origins only)
- CSP headers on all HTTP responses
- `X-Content-Type-Options: nosniff`
- `Strict-Transport-Security: max-age=63072000`
- `Content-Security-Policy: default-src 'self'`

## 6. Data Protection

### 6.1 Encryption at Rest

- PostgreSQL: TDE via filesystem-level encryption on Hetzner VPS (LUKS)
- Optionally: `pgcrypto` for PGP encryption of call context data
- Redis: AUTH password required, no persistent storage for transient data
- Backups: encrypted with GPG before upload to Hetzner Storage Box

### 6.2 Data Retention

| Data Type | Retention | Disposal |
|-----------|-----------|----------|
| Call audio | **Not stored at rest** (default) | N/A |
| Call transcript | Deleted after context returned to agent (max 5 min) | Hard delete |
| Call metadata | 90 days | Anonymized after 90d |
| Call quality metrics | 180 days | Aggregated after 180d |
| Authentication logs | 30 days | Deleted |
| Push tokens | Until device removed or revoked | Deleted |

### 6.3 Controlled Storage (User Opt-in)

If user enables recording:
- Audio stored encrypted (AES-256-GCM)
- Encryption key derived from user password (zero-knowledge)
- Access logged and audited
- User can delete at any time
- Maximum retention: 30 days

## 7. Infrastructure Security

### 7.1 Hetzner VPS Hardening

- Ubuntu 24.04 LTS minimal image
- UFW: only ports 22 (SSH key only), 443 (HTTPS), 3478 (STUN), 5349 (TURN/TLS), 49152-65535 (TURN UDP)
- SSH: key-only, no root login, Fail2ban
- Automatic security updates (unattended-upgrades)
- Docker rootless mode (future)
- Regular security scanning via Trivy (weekly)

### 7.2 Docker Security

- All images based on distroless or slim base images
- No containers run as root
- Read-only root filesystem where possible
- Resource limits per container (CPU, RAM)
- Network isolation (internal networks for services)
- Secrets via Docker secrets or env files (never in image)

### 7.3 TLS Everywhere

- **External:** Caddy reverse proxy with automatic Let's Encrypt TLS
- **Internal:** Service-to-service via Docker network (no TLS needed within network)
- **Mobile:** Certificate pinning (SHA-256 of public key) in production builds

## 8. Audit Logging

```sql
CREATE TABLE audit_log (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    event_type      VARCHAR(50) NOT NULL,  -- 'call.created', 'user.login', 'device.paired', etc.
    actor_id        UUID,                  -- user_id who performed the action
    target_id       UUID,                  -- affected resource ID
    ip_address      INET,
    user_agent      TEXT,
    metadata        JSONB,
    severity        VARCHAR(20) CHECK (severity IN ('debug', 'info', 'warning', 'error', 'critical')),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_audit_actor ON audit_log(actor_id, created_at DESC);
CREATE INDEX idx_audit_event ON audit_log(event_type, created_at DESC);
CREATE INDEX idx_audit_severity ON audit_log(severity) WHERE severity IN ('warning', 'critical');
```

## 9. Incident Response

### 9.1 Alerting Thresholds

| Metric | Threshold | Action |
|--------|-----------|--------|
| Failed auth attempts | >10/min per user | Rate limit + alert |
| Call setup failures | >5% of calls | Alert on-call |
| TURN bandwidth spike | >10x normal | Investigate abuse |
| Unusual call patterns | >50 calls/min from one agent | Review + rate limit |
| JWT signature failures | >5/min | Check for token theft |

### 9.2 Breach Response

1. Isolate affected services (network level)
2. Rotate all secrets (JWT keys, coturn secret, service tokens)
3. Revoke all refresh tokens
4. Force re-pairing of all devices
5. Notify affected users
6. Conduct post-mortem within 48h
